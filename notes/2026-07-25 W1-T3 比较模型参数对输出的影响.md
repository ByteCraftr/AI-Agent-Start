# 2026-07-25 比较模型参数对输出的影响

## 今日目标

理解 `temperature`、`top_p`、`max_output_tokens`、`streaming` 如何影响 LLM 输出，并把结论落到 [[Parenting Copilot]] 的教育建议场景。

## 我先前的理解

参数像普通 API 的配置项，但 LLM 参数会直接影响回答风格、稳定性、完整性和交互体验。教育建议类产品不能只追求“回答丰富”，还要追求稳定、边界清晰和可验证。

## 核心概念

- `temperature`：控制采样随机性。越高，输出越发散；越低，输出越稳定。
- `top_p`：控制候选 token 的概率范围。范围越窄，输出通常越保守。
- `max_output_tokens`：控制最大输出预算。太小会导致回答不完整，甚至没有可提取文本。
- `streaming`：控制返回方式，让用户更快看到内容；它改善体验，不提升内容可靠性。

## 三层理解

概念层：模型参数是控制生成行为的旋钮，决定输出是否稳定、完整、发散、及时。

工程层：参数必须进入请求 payload，并且要尊重模型契约；不是所有模型都支持所有参数。今天的真实调用发现 `gpt-5-mini` 不支持 `temperature` 和 `top_p`。

产品层：[[Parenting Copilot]] 默认应该使用稳定配置，优先保证尊重孩子、安全边界、步骤完整。发散参数更适合头脑风暴，比如生成多个沟通话术或活动方案。

## 验收结果

完成。实验结果显示：

- `stable_default` 能返回完整的亲子教育建议。
- `long_budget` 输出更完整，能包含原则、步骤和注意事项。
- `short_budget` 使用 180 输出 token 时，API 调用成功但没有提取到文本输出，说明输出预算过小会破坏可用性。
- `gpt-5-mini` 明确拒绝 `temperature` 和 `top_p`，说明参数能力属于模型契约，不能假设所有模型都支持。
- `streaming` 本次只记录请求形态，没有实现 SSE 解析。

## 费曼复述

如果给 Android 架构师解释：LLM 参数像 Repository 调远端服务时的请求配置，但它们不是普通 filter 参数，而是会改变远端“生成算法”的行为。`max_output_tokens` 像响应体预算，太小就可能拿不到完整 DTO；`temperature/top_p` 像采样策略，会影响同一输入下返回内容的稳定性。教育类 Agent 默认应该先稳定，再考虑发散。

## 卡点

- 默认模型不支持 `temperature/top_p`，后续如果要专门比较采样参数，需要选择支持这些参数的模型。
- 当前脚本没有解析 streaming 的 SSE 数据流，只记录了 streaming payload 形态。
- 短输出预算导致无文本时，后续可以增强脚本，记录完整响应中的 `status` 和 `incomplete_details`。
