# 2026-07-25 实现第一个 LLM API 调用

## 今日目标

理解一次 LLM API 调用的完整链路，并实现 Parenting Copilot 的第一个最小问答程序。

## 我先前的理解

LLM 调用看起来像普通 HTTP API 调用，但输出不是传统确定性数据，而是受 prompt、上下文和采样参数影响的生成结果。

## 核心概念

一次 LLM 调用需要明确模型、输入消息、采样参数、输出长度、认证方式和错误处理。它是后续 [[结构化输出]]、[[Intent Router]]、[[Agent Loop]] 的基础。

## 三层理解

概念层：它解决把自然语言能力接入应用的问题。

工程层：用代码组装请求 payload，通过 API key 鉴权，发送请求，解析响应，并处理失败。

产品层：让 [[Parenting Copilot]] 能对一个亲子教育问题给出第一版建议，同时保持基本安全边界。

## 今日产物

- 代码：`labs/w01-llm-foundation/parenting_advisor.py`
- 文档：`notes/LLM 应用基础.md`
- 测试：已验证 dry-run payload、Python 语法和缺少 API key 的错误提示。

## 验收结果

完成。真实调用已经返回模型回答；过程中发现 `gpt-5-mini` 不支持 `temperature` 参数，因此脚本改为默认不发送 `temperature`，只在显式传入时附加。

## 费曼复述

LLM API 是 HTTPS 请求，API key 放在 `Authorization` header，body 是 JSON。

HTTPS 会加密传输，但代码、日志、本机代理和服务端仍可能看到明文。

`max_output_tokens` 是输出预算上限，太小会导致回答被截断。

工程上不能假设一次回答一定完整，要检查 response `status` 和 `incomplete_details`。

如果给 Android 架构师解释：LLM API 调用像 Repository 调远端服务，但这个远端服务不是返回固定 DTO，而是根据 prompt 和参数生成回答。所以第一天就要把输入、参数、错误处理、输出长度和完整性检查放进接口设计里。

## 卡点

不要把 API key 写进代码。应通过环境变量 `OPENAI_API_KEY` 注入；如果 key 曾经写入文件或对话输出，应撤销并重新生成。
