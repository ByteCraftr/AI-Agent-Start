## 讨论沉淀

### W2-T2：Prompt 拆分与 Agent 工程设计

本轮重点问题：

- Prompt 拆分为什么属于 Agent 工程设计，而不是单纯提示词技巧？
- 任务边界设计中，Agent 一般怎么识别任务、拆分任务？是否应该依赖 LLM 先拆分？

已确认结论：

- Prompt 可以类比项目里的 `AGENTS.md`：它是给智能体看的运行协议、行为配置和接口契约。
- Agent 工程设计关注的是：LLM 如何接收任务、遵守边界、使用上下文、输出结构化结果、处理失败，并被评估和迭代。
- 任务识别和拆分不应该完全交给 LLM 自由决定。更稳妥的方式是：代码先定义允许的任务空间和流程边界，LLM 在受限选项中做语义判断，代码再校验结构化结果。
- 对 Parenting Copilot，当前推荐先做“有限状态机 + LLM 分类”：`IntentClassifier`、`RiskAssessor`、`InformationChecker` 可以用 LLM，但输出必须受枚举、schema 和本地校验约束。

关键句：

```text
好的 Agent 不是“更会说话的模型”，而是“被工程边界约束住的推理组件”。
```

```text
任务拆分不是“让模型想怎么做就怎么做”，而是“先设计允许的任务空间，再让模型在里面做语义选择”。
```

费曼复述：

```text
Prompt 分层是为了方便分层管理和优化。system prompt 像系统 core，task prompt 像业务实现层，format prompt 像 API 接口。如果不拆分，就不好管理和维护。
```

修正后的架构表达：

```text
Prompt 分层的本质，是把 LLM 的输入设计成可维护的接口：system 管行为边界，task 管本次任务，format 管输出合同。这样 Parenting Copilot 才能在不同问题下保持稳定、安全、可校验。
```

### W2-T1：结构化输出讨论

本轮重点问题：

- `TypeVar("EnumT", bound=Enum)` 是否类似 C++ 模板。
- `enum_type: type[EnumT]` 传入的是不是一个方法。
- `ParentingAdvice` 结构如何让 LLM 知道。
- stream 输出是否需要 stream 输入，以及 stream 输出如何验证。

已确认结论：

- `TypeVar` 可以类比泛型类型参数，但 Python 主要用于类型提示，不像 C++ 模板那样生成多份代码。
- `enum_type` 是枚举类本身，例如 `RiskLevel`，不是普通方法；`enum_type(raw_value)` 会把字符串转换成枚举值。
- LLM 不会自动知道 `ParentingAdvice`，需要通过 JSON Schema、prompt 或 structured output 参数显式告诉它。
- Streaming 是交互层优化，不是可靠性机制。
- `type: object` 表示模型输出顶层必须是 JSON object；`additionalProperties: False` 表示不允许输出 schema 没声明的额外字段。
- schema 声明不等于本地代码已经执行契约；可靠 Agent 要把 prompt 约束、schema 声明和本地校验分开看。

## 关键理解

结构化输出让 Agent 的回答从“自然语言文本”变成“可验证合同”。校验器站在 LLM 和业务系统之间，只有符合合同的输出才能进入 UI、安全策略、评估和后续 Agent Loop。
